# QBOX 复刻项目 —— 数据库实体模型设计（基于 Mock 数据 + 业务功能）

> 版本：v2.0　日期：2026-10-26
> 依据：① 全站 Mock 数据（`frontend/src/api/mock/data/`，全部来自源站登录态抓包实录）；② 项目页面/路由所体现的业务功能；③ `docs/02-数据库设计文档.md` 已核对的源站字段。
> 字段来源标注约定：
> - **[Mock]** = 直接从 Mock/源站抓包字段推导（标注来源接口或数据文件）
> - **[推断]** = Mock 中无该字段，为满足业务逻辑必须补充（标注推导理由）
>
> 本文只做模型设计，不含 SQL。通用约定：主键 `id INT UNSIGNED AUTO_INCREMENT`；时间戳 `createtime`/`updatetime INT UNSIGNED`（与源站 Unix 秒级时间戳一致 [Mock: 所有接口响应]）；软删除 `deleted TINYINT DEFAULT 0` [Mock: MarketDetail 响应含 deleted 字段]。

## 十一、业务约束落地

| # | 约束 | 模型落地 |
|---|------|----------|
| 1 | **实名认证后才能购买/转赠** | `user.real_name_authentication=1`（FK 校验 user_realname.status=1）；订单/挂单/转赠创建入口统一前置校验。`transfer_permission` 独立控制转赠权限 [Mock: getUserInfo 字段] |
| 2 | **交易密码用于支付与转赠确认** | `user.pay_password`（1=已设置，[Mock: getUserInfo.pay_password + account.js]）；密码散列存储于 `user.pay_password_hash` [推断，Mock 不含明文/散列]；pay_record 创建与转赠确认接口强制校验 |
| 3 | **合成消耗指定材料藏品** | `synthesis_recipe_item`（材料=goods + 份数 + user_collection.types）；`synthesis_record.consume_user_collection_ids` 销毁追溯；校验链：user 状态=1 持有 → 锁定 → 合成成功置 3 已售（销毁） |
| 4 | **签到每天一次，连续签到额外奖励** | `UNIQUE(user_id, sign_date)` 保证一天一条；`continuous_days` 对档位 `sign_config.day_no`（实测 7 天周期 s1~s7，每天 1 积分）；补签按 `isfillup/fillupscore(100)/fillupdays(3)` 实测规则扣积分补记 `is_fillup=1` [Mock: monthSign] |
| 5 | **盲盒开启获得随机藏品** | `blind_box_item.probability` 加权随机 + `remain_num` 原子扣减防超发；开启事务内：扣 user_blind_box → 落 blind_box_open_record → 新建 user_collection（collection_code 递增分配）→ 触发 chain_task |
| 6 | **转赠需要对方确认** | 转赠单建议独立 `gift_order`（sender_user_id / receiver_user_id / user_collection_id / status: 1待确认 2已确认 3已拒绝 4已过期，过期由定时任务扫 status+createtime）——确认后写 `trade_record(type=4)` 并迁移 user_collection.user_id [Mock: gift.js 赠送流水 collection_code/price 为确认后落库的流水] |
| 7 | **订单状态机** | `order.order_status`：1待支付 → 2转入成功（pay_record 回调成功）/ 3已取消（超时 surplus_time 或用户取消）；状态流转只允许 1→2、1→3，由后端事务保证；市场单成交同步回写 `market_order.status/order_sn/buy_user_id` 与 `user_collection` 归属 |
